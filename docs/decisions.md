# Decision log

The design decisions behind the factory, each with its reason. The numbers are those of the original decision log;
decisions about one particular installation (its servers, products, accounts and schedule) are not listed.

Record your own installation's decisions below, newest last: number, date, decision, reason. Agents add an entry
(through the record in Gitea) when the owner decides something; nobody edits an earlier entry, a later one amends it.
The supervisor also logs every owner action in Gitea (`factory/factory-records` → `decision-log.md`).

| # | Decision | Reason |
|---|---|---|
| D1 | Build a formal **AI software factory**: agents plan, build, test, review and release; the owner orchestrates. | The owner leads several products with little time at a computer. |
| D3 | **One interface** for the owner, usable from phone, tablet and laptop. No terminal and no SSH for the owner. | Minimal interaction with a minimal number of interfaces; the owner works mostly from a phone. |
| D4 | The interface is a **chat cockpit**, self-hosted, reachable only over Tailscale. Hosted chat services were considered and rejected (third-party data, not a system of record). | Confidentiality of product and client material. |
| D5 | **Zulip** is the cockpit (over Mattermost and Element). | Topics map one-to-one to tasks; free mobile push for up to 10 users on the self-hosted Free plan; end-to-end encrypted push since Zulip Server 12.0; simple bot API; simpler to host. Mattermost's free push is for non-commercial use only and its ID-only push needs an Enterprise-level plan. |
| D6 | **Gitea** is the record in the background: tasks (issues), code, reviews, CI (Gitea Actions), decision log. The owner does not need to open it. | A structured, auditable system of record that works with local CI. A hosted forge can stay as backup and release mirror. |
| D7 | **OMP** is the agent engine, run **headless** by a supervisor (`--mode rpc --no-ui`, `--resume`, `--profile`). | It supports headless operation, sessions that resume, and profiles per product. |
| D8 | **One OMP installation, on the factory server only.** All memory, skills, sessions, settings and logins in one place. Other machines (Windows build PC, lab host) run **no OMP**; they are only "hands" that execute jobs and report back. | Scattered OMP installations would split memory and features. |
| D9 | Model access for OMP is **set up by the owner**; the factory needs only a working OMP login. | Providers, plans and their terms are the owner's choice; agents do not decide them. |
| D10 | The factory is packaged as **containers** (Docker Compose) and host services that run on a VPS or locally; heavy or Windows/VM work runs on separate "hands" machines. | Portable: deploy anywhere, move with a backup. |
| D16 | **One Zulip channel per product**; each channel holds that product's tasks (one topic per task). New products are registered on request (Gitea project + channel + agent user); channels the owner creates by hand are plain chat channels. `#factory` stays for chat across products, digests and decisions. | Each product's work stays together and can be muted or followed on its own. |
| D17 | The owner may **merge with red or missing gates** by saying so with a reason (`merge anyway: <reason>`; no conflicts; a pull request that changes the gates also needs the gate-change form, `merge anyway with gate change: <reason>`), and may send a finished or paused task **back to its agent** with `rework` / `rework: <note>` (update the branch against the default branch, resolve conflicts, gates again). | Shipping with a known red gate is the owner's call (decision policy), and conflicting pull requests must be fixable from Zulip. Every use is in the decision log with its reason. |
| D22 | **The factory signs release packages outside CI** ([infra/signer](../infra/signer/factory-signer), README "Signed release packages"). CI builds an **unsigned** release package on every branch. The signer is a timer on the factory server, running as the user `factory-signer` (no login, no Docker; one sudo rule for a root helper that reads the artifact from Gitea's storage). It signs only the newest successful gates run on `main`, verifies the certificate against the key, and publishes a Gitea pre-release `android-<sha>` with `<Name>-<version>-<sha>.apk`. **The key never enters Gitea (not even as a secret), a repository, an agent's workspace or a model's context**: it lives in `/srv/factory/signer` (0700) and in the encrypted backup. The Gitea bot `factory-signer` has token scope `write:repository` (Gitea has no narrower one for releases); team `release-signer` limits it to code read, Actions read and releases write. Tags `android-*` are protected so only that bot can create or delete them. The default gates run on branch pushes only. Products are added with `infra/signer/add-product.sh`; `factory.sh install` sets up the signer empty, and `restore` brings back its keys. Android is built; Windows (`osslsigncode`, a bought certificate) is a hook only. | Any workflow on a `task/*` branch, which the agents write, can read repository secrets, so a key in Gitea is a key the agents hold. Only `main`, which only the owner's `merge` reaches, is signed. Gitea 28.1's API serves only v4 artifacts, hence the root fetch helper. Without the tag protection, a product agent's `write:repository` token could publish a release that looks signed. Gates on tags would rerun the full build for every release tag. |
